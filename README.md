# Мини-CRM «Объекты и задачи»

Тестовое приложение для строительной компании. Постановщик ведёт объекты и ставит задачи, исполнитель работает только со своими назначениями. Статус меняется по фиксированному циклу, каждый переход пишется в историю.

Демо: https://crm-construction-ten.vercel.app

## Стек

- React 19, TypeScript, Vite
- Tailwind CSS, React Router
- Supabase: Postgres, Auth, RLS

## Локальный запуск

Нужен **Node.js 22**.

1. Скопируйте `.env.example` в `.env`.
2. В настройках проекта Supabase (Settings → API) возьмите URL и ключ **anon / publishable**. Подставьте их в `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Во фронтенд кладётся только этот публичный ключ.
3. Установите зависимости и запустите:

```bash
npm i
npm run dev
```

## База данных

- Миграции: `supabase/migrations`
- Демо-данные: `supabase/seed.sql`

Как применить:

- **SQL Editor** в кабинете Supabase: сначала файл миграции, затем `seed.sql`.
- **CLI**: `supabase db push` для миграций; seed выполните в SQL Editor или через `psql` к проекту.

В Auth оставьте открытую регистрацию **выключенной** (Disable signup). Пользователь без роли и профиля в приложение не попадёт.

## Роли и цикл статусов

| Роль | Доступ |
| --- | --- |
| Постановщик | Все объекты и задачи. Создаёт и правит объекты; создаёт задачи; меняет название, описание и исполнителя без смены статуса. Принимает работу или возвращает на доработку (любой постановщик, не только автор). |
| Исполнитель | Только свои задачи и объекты, где они есть. Берёт в работу, отправляет на проверку, возвращает с доработки в работу. Поля задачи не редактирует. |

| Из | В | Кто |
| --- | --- | --- |
| Новая | В работе | назначенный исполнитель |
| В работе | На проверке | назначенный исполнитель |
| На проверке | Принята | любой постановщик |
| На проверке | На доработке | любой постановщик, с комментарием |
| На доработке | В работе | назначенный исполнитель |

## Безопасность

Права проверяются в базе (RLS), а не только в интерфейсе. Статус меняется исключительно через RPC `transition_task`. История статусов неизменяема: клиент может её читать, но не писать и не править. Во фронтенде нет привилегированных ключей — только anon/publishable.
